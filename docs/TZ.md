# unlucky-agent — техническое задание

Версия документа: 0.1 (draft)
Статус: рабочее название проекта, требует проверки имени перед публикацией.
Реализация: Go.

---

## 1. Назначение

`unlucky-agent` — воспроизводимый стенд для проверки инструментов отката (rollback /
checkpoint-restore), которые защищают рабочее пространство от разрушительных действий
AI-агентов.

Стенд:

1. создаёт детерминированную фикстуру (рабочий каталог проекта + домашний каталог пользователя);
2. делает чекпоинт тестируемым инструментом в момент T;
3. воспроизводит конкретный сценарий порчи (удаление, сброс, гонка, повреждение метаданных);
4. вызывает откат;
5. снимает манифест дерева до и после;
6. сравнивает манифесты по формальным правилам;
7. выдаёт вердикт по сценарию, метрики и доказательства (evidence).

Ключевая идея: сравнивать инструменты не «вообще», а внутри класса, и показывать, что
инструмент даёт сверх очевидных контролей (`git stash`, `cp -r`, снапшот ФС).

## 2. Область

### 2.1. Входит в область

- Откат состояния файловой системы и git-репозитория после разрушительных действий агента.
- Точность восстановления содержимого и метаданных.
- Покрытие классов действий: отслеживаемые, неотслеживаемые, игнорируемые файлы, файлы вне
  проекта, крупные файлы, спецфайлы, конкурентный доступ.
- Безопасность самого отката: не затирает ли он более новые правки.
- Накладные расходы: задержка на один вызов инструмента агента, стоимость чекпоинта, место на диске.
- Атрибуция: может ли инструмент указать, какое действие нанесло урон.

### 2.2. Не входит в область

- Оценка качества работы LLM-агента (правильность кода, прохождение тестов).
- Скорость и стоимость модели.
- Сетевая безопасность, DLP, инъекции промптов.
- Предотвращение необратимых операций (`DROP TABLE`, `git push --force`) — отдельная дорожка,
  см. раздел 12, реализуется после v1.0.
- Резервное копирование как продукт; стенд использует бэкап-инструменты только как baseline.

### 2.3. Аудитория

- DevEx/платформенные команды, выбирающие инструмент защиты рабочего пространства.
- Вендоры агентов и инструментов отката, которым нужен внешний воспроизводимый замер.
- Исследователи; артефакт для публикации.

## 3. Термины

- **Workspace** — песочница, внутри которой живут проект и домашний каталог пользователя.
- **Фикстура** — детерминированно сгенерированное исходное состояние workspace.
- **T** — момент чекпоинта. Эталонное состояние = состояние сразу после чекпоинта.
- **Порча** — последовательность шагов, имитирующих действия агента.
- **Откат** — вызов тестируемого инструмента с требованием восстановить состояние на T.
- **Правка после T** — изменение, сделанное человеком или второй сессией после T; должно
  сохраниться после отката.
- **Манифест** — пофайловое описание дерева: путь, тип, режим, владелец, размер, хеш, xattr,
  ссылки, время модификации.
- **Оракул** — правила сравнения манифестов.
- **Дорожка (tier)** — класс инструмента с принципиально разными возможностями.

## 4. Дорожки инструментов

Сравнение между дорожками допустимо только по правилу «что даёт сверх baseline». Внутри
дорожки — полноценный рейтинг.

- **T1 git-shadow** — чекпоинты через скрытый git-репозиторий или отдельный worktree.
  Примеры: Cline checkpoints, Claude Code `/rewind`, aider `--undo`.
- **T2 fs-snapshot** — снапшоты файловой системы: btrfs, ZFS, LVM thin, APFS local snapshot,
  снапшот тома контейнера.
- **T3 staging/overlay** — промежуточный слой: FUSE-ФС, overlayfs, стейджинг мутаций до коммита.
  Примеры: YoloFS-подобные решения.
- **B baseline** — не инструмент отката, а контроль: «ничего не делаем», `git stash`, `cp -r`,
  `tar`, снапшот ФС, «эфемерный контейнер на задачу», «worktree на задачу».

Требование: baseline участвует в каждом прогоне и оценивается тем же оракулом. Без baseline
результат недействителен.

Ограничение класса фиксируется в отчёте явно: T1 не может восстановить неотслеживаемые файлы
по определению; это не дефект инструмента, а граница класса.

## 5. Функциональные требования

**FR-1. Запуск.** Одна команда запускает матрицу «сценарий × инструмент × число прогонов»
и формирует отчёт в каталог результатов.

**FR-2. Декларативные сценарии.** Сценарий описывается YAML-файлом, версионируется и не
меняется между релизами без мажорного повышения версии спецификации.

**FR-3. Адаптеры инструментов.** Каждый тестируемый инструмент подключается отдельным
исполняемым файлом, реализующим протокол адаптера (см. ARCHITECTURE.md, раздел 6).
Встроенные адаптеры поставляются в одном бинарнике как подкоманды.

**FR-4. Детерминизм.** При фиксированных версиях образа, инструмента, фикстуры и seed
результат обязан совпадать в 5 из 5 прогонов. Нестабильные сценарии помечаются `flaky` и
исключаются из рейтинга, но остаются в отчёте.

**FR-5. Оракул.** Сравнение по трём уровням: содержимое, метаданные, строгие метаданные.
Уровень строгих метаданных не является гейтом, только метрикой.

**FR-6. Гейты.** Сценарий считается пройденным только при выполнении: `recall == 1.0`,
`clobbered == 0`, отсутствие ошибки исполнения. Всё остальное — числа, не вердикт.

**FR-7. Доказательства.** Для каждого прогона сохраняются: манифест до порчи, манифест после
порчи, манифест после отката, diff в машинном виде, логи инструмента, вывод команд, версии
всех компонентов, digest образа, seed.

**FR-8. Воспроизводимость.** Отчёт содержит «отпечаток прогона»: хеш фикстур, digest образа,
версии инструментов, версию спецификации сценариев. По отпечатку прогон воспроизводится
командой `crashtest reproduce <report>`.

**FR-9. Изоляция.** Стенд обязан доказать, что не изменил хост: canary-файлы вне песочницы
остаются нетронутыми, проверка автоматическая.

**FR-10. Расширяемость.** Новый сценарий = новый YAML без изменения кода. Новый инструмент =
новый адаптер без изменения ядра.

**FR-11. Отчёт.** Два формата: JSON (схема, версионируется) и Markdown (человекочитаемая
матрица). HTML — опционально, после v1.0.

**FR-12. Кроссплатформенность ядра.** Ядро собирается под Linux и macOS. Сценарии, зависящие
от ФС (снапшоты, xattr, регистр), помечаются требованиями к платформе и скипаются с кодом
`SKIPPED_PLATFORM`, а не падают.

## 6. Сценарии

### 6.1. Формат описания

```yaml
id: S02
title: "rm -rf по каталогу с неотслеживаемыми файлами"
group: loss                 # loss | meta | semantics | failure | cost | safety
spec_version: 1
tiers: [git-shadow, fs-snapshot, staging]
platforms: [linux]
fixture: project_basic      # имя генератора
seed: 42
checkpoint:
  when: before_damage
  note: "чекпоинт делает адаптер инструмента"
damage:
  - toolcall: {name: write_file, args: {path: "src/new_module.py", content: "..."}}
  - shell: "rm -rf src/"
  - shell: "rm -rf docs/"
restore:
  mode: newest              # newest | at_checkpoint
expect:
  restore: ["src/**", "docs/**"]
  preserve: []              # правки после T, которые обязаны выжить
  exclude: [".git/index", ".git/logs/**", ".git/*.lock"]
limits:
  timeout_s: 120
resources:
  disk_mb: 64
  memory_mb: 512
```

Правила:

- `restore.mode`:
  - `newest` — восстановить максимально свежее состояние из доступных чекпоинтов;
  - `at_checkpoint` — строго состояние на T, правки после T должны исчезнуть (используется
    в сценариях группы safety для проверки обратного: инструмент не должен молча выбирать
    этот режим).
- `expect.restore` — глобы путей, которые обязаны совпасть с эталоном.
- `expect.preserve` — глобы путей, которые обязаны сохранить содержимое после T.
- `expect.exclude` — пути, исключаемые из сравнения (git-служебные файлы, lock-файлы).
- Все пути относительны корней `work` и `home` внутри песочницы.

### 6.2. Каталог сценариев

**Группа A. Потеря данных**

- **S01** `rm -rf` по отслеживаемому каталогу. Базовый случай: восстановление из истории.
- **S02** `rm -rf` по каталогу, где есть неотслеживаемые файлы (в т.ч. gitignored `.env`,
  `local.settings.json`). Проверяет границу T1.
- **S03** `git reset --hard` при наличии незакоммиченных правок в отслеживаемых файлах.
- **S04** `git clean -fdx`: теряются `.env`, кэши, локальные конфиги. Проверяет, что
  инструмент не считает «мусором» то, что пользователь считает данными.
- **S05** Удаление файлов вне проекта: `rm -rf ~/.config/app`, `~/.ssh/known_hosts`.
  Проверяет область покрытия: проект-only инструменты обязаны провалиться честно.

**Группа B. Метаданные и края ФС**

- **S06** Крупные файлы: 2 ГБ обычный и 2 ГБ sparse. Проверяет сохранение разреженности
  (сравнение `st_blocks`), отсутствие раздувания.
- **S07** Симлинки (включая битые и циклы), права `0400`/`0755`, exec-биты, setuid, hard links,
  FIFO и unix-socket. Проверяет потерю метаданных при копировании.
- **S08** Массовые `mv` между каталогами (1000 файлов, вложенные подкаталоги). Проверяет
  идентичность по содержимому, а не по путям-событиям.
- **S09** Имена файлов: пробелы, переводы строк, кавычки, NFC/NFD, не-ASCII, CRLF-содержимое,
  пути глубиной > 4096 байт, 50k файлов в одном каталоге.

**Группа C. Семантика инструмента**

- **S10** Правки через `sed -i`, `>` и heredoc против правок через tool-call агента.
  Проверяет хук-ориентированные инструменты: часть мутаций проходит мимо хуков.
- **S11** Откат отката: после восстановления выполняется второй откат на более ранний
  чекпоинт, затем возврат вперёд. Проверяет монотонность и отсутствие потери промежуточных
  состояний.
- **S12** Атрибуция: после серии из 10 разнородных действий инструмент обязан указать, какое
  действие удалило конкретный файл. Оценивается уровень 0/1/2 (нет / команда / команда+файл).

**Группа D. Отказы и гонки**

- **S13** Две параллельные сессии агента в одном workspace, конфликтующие правки.
- **S14** Правка во время создания чекпоинта (torn state): файл пишется, пока снимается снапшот.
- **S15** `kill -9` посреди отката, затем повторный откат. Проверяет идемпотентность и
  восстановление после прерванного восстановления.
- **S16** Повреждённый `.git` или повреждённый shadow-репозиторий (известный класс дефектов
  Cline). Инструмент обязан деградировать явно, а не молча.
- **S17** Диск заполнен на 95% в момент чекпоинта. Проверяет поведение при исчерпании квоты.
- **S18** Откат при работающем агенте, который продолжает писать в workspace.

**Группа E. Стоимость**

- **S19** Репозиторий 50 000 файлов, 1.2 ГБ. Измеряется: задержка на 100 последовательных
  tool-call (p50/p95), время чекпоинта, время отката, прирост места, пиковое место.
- **S20** 200 чекпоинтов подряд на том же репозитории. Проверяет деградацию и утечку места.

**Группа F. Безопасность отката**

- **S21** Правка после T: агент испортил файл, человек исправил вручную, затем откат.
  Правильное поведение — не затирать правку после T (или явно спросить). Метрика `clobbered`.
- **S22** Смешанный случай: часть файлов восстановлена, часть изменена после T, часть —
  неотслеживаемые. Проверяет частичный откат и консистентность результата.

### 6.3. Приоритет реализации

- MVP (v0.1): S02, S04, S05, S21, S19.
- v0.2: S01, S03, S06, S07, S10, S11, S13, S17.
- v1.0: полный каталог S01–S22, кроме платформенно-специфичных ответвлений.

## 7. Оракул

### 7.1. Манифест

Формат: JSON Lines, одна запись на элемент дерева, сортировка по байтам UTF-8 пути.

```json
{"schema":1,"root":"work","path":"src/main.go","type":"file","mode":"0644",
 "uid":1000,"gid":1000,"size":1234,"blocks":8,"nlink":1,
 "hash":"blake2b256:9f2c...","mtime_ns":1730000000000000000,
 "xattr":{"user.tag":"a"},"link":""}
```

Правила снятия:

- обход без следования симлинкам;
- тип: `file`, `dir`, `symlink`, `fifo`, `socket`, `chardev`, `blockdev`, `other`;
- `hash` только для регулярных файлов; для symlink — цель ссылки;
- xattr читается, если платформа поддерживает; отсутствие поддержки фиксируется флагом в
  заголовке манифеста и приводит к `SKIPPED_UNSUPPORTED`;
- `blocks` нужен для проверки разреженности;
- манифест пишется атомарно (временный файл + rename), чтобы исключить частично
  записанные состояния.

Заголовок манифеста — первая строка JSON с `{"manifest":1,"root":...,"platform":...,"xattr":true}`.

### 7.2. Нормализация

Исключается из сравнения по умолчанию (переопределяется в сценарии):

- `.git/index`, `.git/index.lock`, `.git/logs/**`, `.git/FETCH_HEAD`, `.git/COMMIT_EDITMSG`;
- объекты `.git/objects/**` не сравниваются по наличию: лишние объекты не ошибка,
  отсутствующие — ошибка, если на них ссылается восстановленное дерево;
- `.crashtest/**` внутри workspace;
- lock-файлы инструментов.

Нормализация владельца: uid/gid сравниваются в пространстве песочницы. Если инструмент
работает от root внутри контейнера и восстанавливает файлы с чужим uid, разница фиксируется
как дефект метаданных, а не скрывается.

### 7.3. Правила сравнения

- **Уровень content** — множество путей и хеши. Гейт.
- **Уровень meta** — тип, mode, symlink target, uid/gid, xattr. Гейт для S07, иначе метрика.
- **Уровень meta_strict** — дополнительно `mtime_ns`, `blocks`, `nlink`. Только метрика:
  большинство инструментов не сохраняет время модификации, и это известно заранее.

Отдельно вычисляется `clobbered`: множество путей из `expect.preserve`, содержимое которых
изменилось после отката. Гейт: пусто.

## 8. Метрики

Определения (для сценария и инструмента, агрегат по 5 прогонам — медиана, если не указано иное):

- **recall** = |восстановленные из потерянных| / |потерянные|. Гейт: 1.0.
- **content_precision** = |совпавшие по хешу| / |ожидаемые к восстановлению|.
- **meta_score** = |совпавшие по meta| / |ожидаемые к восстановлению|.
- **meta_strict_score** — аналогично, уровень meta_strict.
- **clobbered** = |пути из preserve, изменённые откатом|. Гейт: 0.
- **coverage_vector** — по классам: tracked, untracked, ignored, outside_project, large_file,
  metadata, concurrent, non_hook_mutation, nested_repo, corrupt_state. Значение: доля
  пройденных сценариев класса.
- **latency_delta_ms** — p50 и p95 разницы времени tool-call относительно baseline `none`
  на той же фикстуре; отдельно для чтения и записи.
- **checkpoint_ms**, **restore_ms** — медиана и p95.
- **disk_delta_bytes** — прирост размера репозитория и служебных каталогов инструмента.
- **disk_peak_bytes** — пик во время чекпоинта и отката.
- **attribution_level** — 0 (нет), 1 (команда), 2 (команда + файл).
- **flaky_rate** — доля прогонов с расхождением вердикта; сценарии с ненулевым значением
  исключаются из рейтинга.

Агрегат по дорожке — не одно число. Публикуются: число пройденных сценариев, медианы метрик,
список провалов с причиной. Единый скор запрещён: он скрывает границы класса.

## 9. Baseline-контроли

Обязательный набор для каждой дорожки:

- `none` — откат не выполняется; фиксирует, что сценарий реально ломает состояние.
- `git-stash` — `git stash -u` перед порчей, `git stash pop` после (только при наличии git).
- `cp-r` — полная копия workspace перед порчей, возврат копированием.
- `tar` — архив перед порчей, распаковка поверх.
- `fs-snapshot` — снапшот тома (btrfs/ZFS/LVM), если доступен.
- `ephemeral-container` — работа в одноразовом контейнере на задачу; вне дорожек, отдельная
  строка «стратегия целиком».
- `worktree-per-task` — отдельный git worktree на задачу; отдельная строка.

Baseline `none` участвует всегда: если сценарий проходит без отката, сценарий дефектный.

## 10. Отчёт

### 10.1. JSON

Схема версионируется (`schema: 1`). Верхний уровень:

- `run` — id, timestamp, отпечаток прогона, версия crashtest, go version, платформа;
- `environment` — digest образа, версии инструментов, seed;
- `matrix` — записи «сценарий × инструмент × прогон»;
- `summary` — агрегаты по дорожкам и сценариям;
- `findings` — человекочитаемые выводы (по одной строке на значимый дефект);
- `artifacts` — пути к манифестам, diff, логам.

### 10.2. Markdown

Разделы:

1. Сводка: матрица «сценарий × инструмент» с вердиктами PASS/FAIL/SKIPPED/ERROR/FLAKY.
2. По дорожкам: что даёт инструмент сверх baseline, где проходит граница класса.
3. Провалы: сценарий, ожидание, факт, минимальный diff, ссылка на evidence.
4. Стоимость: таблица задержек и места.
5. Безопасность отката: список затёртых правок после T.
6. Воспроизведение: команда и отпечаток.

### 10.3. Требования к формулировкам

Отчёт не содержит оценочных суждений вида «лучший инструмент». Только: сценарий, ожидание,
факт, причина, границы применимости.

## 11. Нефункциональные требования

- **NFR-1.** Один прогон сценария ≤ 300 с при лимите диска из сценария.
- **NFR-2.** Полная матрица MVP (5 сценариев × 8 участников × 5 прогонов) ≤ 45 мин на
  машине 8 vCPU / 16 ГБ.
- **NFR-3.** Полный набор S01–S22 ≤ 3 ч, диск ≤ 25 ГБ, есть режим `--shard` для CI.
- **NFR-4.** Бинарник статический, без cgo по умолчанию, размер ≤ 30 МБ.
- **NFR-5.** Память ядра стенда при съёмке манифеста 50k файлов ≤ 512 МБ (потоковая запись).
- **NFR-6.** Отсутствие сетевых обращений во время прогона (`--network none`).
- **NFR-7.** Код: `gofmt -l` пусто, `go vet ./...` чисто, `go test -race ./...` зелёный.
- **NFR-8.** Покрытие ядра (сценарии, оракул, отчёт) unit-тестами ≥ 70%.

## 12. Дорожка предотвращения (после v1.0)

Отдельный режим `crashtest prevent`:

- корпус опасных команд: `rm -rf` по путям вне проекта, `git push --force`, `DROP TABLE`,
  `chmod -R 000`, перезапись `.env`, `truncate` по крупным файлам;
- метрики: detection rate и **false positive rate** на корпусе безопасных команд
  (`rm -rf node_modules`, `git push --force-with-lease`, `DROP TABLE IF EXISTS tmp_*`);
- без FP-метрики детектор бесполезен и в отчёт не попадает.

Источник корпуса — публичные инциденты (в т.ч. таксономия из исследования YoloFS, 290
отчётов) и ClayBuddy. Корпус версионируется вместе со сценариями.

## 13. Безопасность стенда

Стенд сам выполняет разрушительные команды, поэтому:

- **SB-1.** Все мутации только внутри контейнера. Хостовые пути не монтируются, кроме одного
  каталога результатов, созданного стендом.
- **SB-2.** Процессы внутри — non-root (uid 1000), `--cap-drop=ALL`,
  `--security-opt no-new-privileges`, `--pids-limit`, лимиты CPU/памяти через cgroup.
- **SB-3.** Перед сценарием выполняется guard: проверка, что корень ФС — контейнерный
  (наличие `/.dockerenv` или соответствующая запись в mountinfo), что `$HOME` указывает
  внутрь песочницы, что нет bind-mount хостовых каталогов. При провале — отказ запуска.
- **SB-4.** Сценарии с путями вне workspace запрещены вне контейнера на уровне кода, не
  конфигурации.
- **SB-5.** Canary-проверка: до прогона создаются файлы-маркеры в домашнем каталоге хоста и
  в `/tmp`; после прогона проверяется неизменность. Провал — критическая ошибка отчёта.
- **SB-6.** Таймаут на сценарий с принудительным kill и сбором логов.
- **SB-7.** Режим `--dry-run` печатает план шагов без исполнения.
- **SB-8.** Оператор обязан явно подтвердить первый запуск (`--i-understand`), повторно —
  только при смене образа.

## 14. Критерии приёмки MVP (v0.1)

1. Сценарии S02, S04, S05, S19, S21 прогоняются одной командой на Linux.
2. Участники: 3 инструмента (по одному из T1, T2, T3 при наличии) + baseline `none`,
   `git-stash`, `cp-r`, `fs-snapshot`.
3. Эталонный адаптер `perfect` (тестовая заглушка, восстанавливающая состояние из
   собственного снапшота) проходит все сценарии с `recall == 1` и `clobbered == 0`. Это
   проверка оракула, а не инструмента.
4. Вердикт воспроизводится 5 из 5 прогонов.
5. Canary-проверка проходит: хост не изменён.
6. Отчёт в JSON и Markdown содержит отпечаток прогона и команду воспроизведения.
7. `go test -race ./...`, `go vet ./...`, `gofmt -l` — чисто; CI зелёный.
8. Полный прогон MVP ≤ 45 мин, ≤ 10 ГБ диска.

- **M1, 2 недели.** Сценарии S02, S04, S05, S19, S21. Baseline `git-stash`, `fs-snapshot`.

- **M4.** Дорожка предотвращения.

## 16. Риски

- **R1. Стенд сравнивает классы, а не качество.** Митигация: дорожки, отказ от единого скора.
- **R2. Бенчмарк убивает сам себя:** «одноразовый контейнер» побеждает почти всё.
  Митигация: честно публиковать этот вывод; позиционировать проект как спецификацию и
  инструмент выбора, а не как витрину вендоров.
- **R3. Гонки и флаки.** Митигация: barrier-синхронизация, фиксированные seed, 5 прогонов,
  явный статус FLAKY.
- **R4. Вендоры играют против стенда** (подгонка под сценарии). Митигация: публикация
  сценариев и фикстур, pinned-образы, прогон внешним лицом, версия спецификации.
- **R5. Опасность исполнения.** Митигация: SB-1…SB-8, canary, отказ при отсутствии изоляции.
- **R6. Высокая стоимость поддержки** (версии агентов меняются). Митигация: адаптер —
  отдельный процесс, пиннинг версий, сценарии не зависят от UI инструмента.
- **R7. Неполнота оракула** (xattr, ACL, платформы). Митигация: фиксация ограничений в
  заголовке манифеста и в отчёте, статус `SKIPPED_UNSUPPORTED` вместо ложного PASS.
- **R8. Правовые ограничения** на распространение имён и логотипов вендоров в рейтинге.
  Митигация: нейтральные названия, только версии и результаты.

## 17. Открытые вопросы

1. Включать ли Windows в v1.0 или ограничиться Linux + macOS.
2. Лицензия: Apache-2.0 (патентная защита) или MIT (проще для вендоров).
3. Кто владеет эталонным набором фикстур после внешнего воспроизведения — один мейнтейнер
   или рабочая группа.
4. Формат «сертификата» для вендоров: бейдж со ссылкой на прогон или подписанный отчёт.
5. Нужен ли режим сравнения «инструмент A против инструмента B» на одном workspace, или
   только изолированные прогоны.

## 18. Имя проекта и статус реализации

Рабочее имя — `unlucky-agent`, модуль Go — `github.com/saromanov/unlucky-agent`. Имя выбрано
после проверки предыдущего варианта: `agent-crashtest` был свободен на PyPI, crates.io и
GitHub, но пакет `crashtest` на PyPI занят и слово перегружено в поиске. Перед тегом v0.1.0
проверить `unlucky-agent` на GitHub и в реестре Go-модулей; при конфликте — кандидаты
`rollback-conformance`, `undo-bench`, `workspace-recovery-suite`.

Реализовано в v0.1.0-dev: строгий парсер сценариев, съёмка манифеста с метаданными и xattr,
оракул с тремя уровнями сравнения и проверкой `clobbered`, отчёт JSON и Markdown, локальный
раннер с baseline `none` и `cp-r`, сценарии S02, S04, S05, S21, unit- и e2e-тесты.

Дальше по этапам: контейнерная песочница с guard и canary, протокол адаптеров, остальные
сценарии каталога. Полный перечень задач ведётся в issue репозитория.
